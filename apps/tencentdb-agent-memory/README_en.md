# TencentDB Agent Memory

Tencent Cloud's agent long-term memory service builds progressive context from L0 conversations, L1 atomic memories and L2 scenes to L3 profiles. This app packages the complete official three-component stack:

| Component | Image | Default host port | Purpose |
| --- | --- | --- | --- |
| Memory Core | `agentmemory/memory-core` | 8420 (localhost only) | Memory, metadata and user authentication |
| Memory Hub | `agentmemory/memory-hub` | 8125 / 8424 | Web panel / Knowledge API |
| Memory Proxy | `agentmemory/memory-proxy` | 8096 | LLM forwarding, session initialization and context injection |

Pinned `1.0.3` and rolling `latest` packages are provided. All three images support amd64 and arm64. The package uses local SQLite and BM25, without Redis, MongoDB, Tencent Cloud VectorDB or COS. Model APIs are required separately. Allow at least 4 GB RAM as a starting point and measure your actual workload.

## Installation

- **Memory LLM**: supply an OpenAI-compatible API URL, key and model. Core and Hub share these settings for memory extraction, summaries and knowledge processing. Choose a model with suitable context/output limits; API usage may incur charges.
- **Proxy upstream**: supply the API URL and key used for your coding agent's actual model requests. This can differ from the memory LLM. The requested model is forwarded from the client, not overridden by this package.
- **Prompt mode**: choose `code` for engineering/team workflows, or `chat` for personal assistants and conversations.
- **Admin username/key**: used for initial bootstrap. Save the key randomly generated by 1Panel. After initialization, `data/core/.admin-key` is authoritative; changing the form does not rotate an existing user key.
- **Service keys**: use independent random secrets for Panel/Knowledge communication and Proxy administration. These are not user keys.

## Listening Addresses and URLs

All host ports default to localhost. For an initial test, use SSH forwarding:

```bash
ssh -L 8125:127.0.0.1:8125 -L 8096:127.0.0.1:8096 user@server
```

To allow LAN access to Panel, Knowledge and Proxy, set the bind address to the server's interface IP or `0.0.0.0` and configure firewall rules. For internet access, prefer an HTTPS reverse proxy plus additional access controls. Core always binds its host mapping to localhost regardless of this setting.

- **Client-facing Proxy URL**: the URL clients can actually reach, e.g. `http://192.168.1.10:8096` or an HTTPS domain. The default localhost address is only suitable for local/SSH-forwarded use. Panel uses this value to generate client connection addresses.
- **Knowledge URL**: leave empty to automatically use Hub's internal container URL; internal workflows do not require exposing a host port. For remote tools, set a URL reachable by all callers, including Core, and ending in `/v3`, e.g. `http://192.168.1.10:8424/v3`. Update this URL when changing public ports.
- Containers can access host model services through `host.docker.internal`, provided the host service listens on a container-reachable interface.

## First Use

1. Wait for all services to become healthy. The Core adapter initializes and verifies the administrator before allowing Hub and Proxy to start.
2. Open `http://127.0.0.1:8125` (or your configured panel URL), select instance `default` and log in with your admin username and user key.
3. Create teams, agents, tasks and regular users. Use Panel's generated client connection address rather than assuming a bare `/v1` path works; upstream requires client/instance routing prefixes.
4. Proxy enables `auth`, `sessionInit`, `tdai`, and the skill/knowledge/tdai-memory injectors. Supply the platform user key as required by upstream client integrations (such as `x-tdai-user-key`), not your model provider's key.

The saved administrator key is in the actual app installation directory at `data/core/.admin-key`. Do not disclose it in logs or screenshots.

Health endpoints, using default ports:

```bash
curl http://127.0.0.1:8420/health
curl http://127.0.0.1:8125/health
curl http://127.0.0.1:8424/health
curl http://127.0.0.1:8096/health
```

Health checks cover process liveness and admin initialization, not successful model access, ingestion or extraction. Verify those with real sessions.

## Persistence and Updates

```text
data/
├── core/       # SQLite, memories and .admin-key
├── hub/        # Knowledge SQLite, files, SSH keys and logs
├── proxy/      # Proxy SQLite
└── scripts/    # 1Panel startup adapters; do not remove
```

Core and Proxy config is safely serialized from environment variables into temporary files on every start. To apply changed model settings, save and recreate/update the containers in 1Panel; restarting alone does not change container environment variables.

The Proxy adapter prepares its bind-mounted directory as root, then drops to uid/gid `10001` before running the application. No `chmod 777` is needed.

Stop the complete stack before backing up all of `data/`, Compose and installation environment settings. Restore databases together with their matching `.admin-key`. Prefer pinned releases for production, back up before upgrading `latest`, and never share SQLite directories across concurrent instances.

## Security and Upstream Limitations

Upstream Proxy authentication does not send the Core Gateway Bearer token. This package therefore disables the Core Gateway Bearer gate, but connects Core only to a per-install `memory-stack` network, not the shared `1panel-network`. Hub and Proxy join both networks. **Never publish Core through an internet-facing reverse proxy.** The internal `local` token is only a feature-registration marker, not a security secret.

Knowledge write/admin endpoints require the service key, but some query endpoints are public. Proxy management uses its separate admin key. User authentication does not protect every HTTP route: audit endpoints and add access controls before exposing the stack. Private CostGuard extensions are disabled. MongoDB, cloud storage and multi-replica service mode are outside this package's scope.
